# V4 开发顺序建议

## 1. 总原则

- 先冻结方法与公式，再落代码。
- 先统一权威评价链，再改求解器和页面。
- 先修复“后台计算顺序错误”，再修复“前台表达顺序混淆”。
- V4 计算引擎与 Streamlit 页面解耦；界面层不得自行拼装另一套目标值。

## 2. V4 推荐开发顺序

### 1. 冻结方法与公式

- 依据科技报告、任务说明和中期 PPT 冻结正式科研方法流程、算法内部评价流程、网页展示流程。
- 冻结区域协同在优化中的正式位置。
- 明确哪些内容有正式依据，哪些内容待完善、待标定、待确认。

### 2. 建立唯一候选方案评价函数

- 建立唯一权威的村域候选方案评价函数。
- 统一该函数的输入、输出、中间结果和约束返回结构。
- 禁止精确枚举和 NSGA-II 各自维护一套私有评价逻辑。
- 第一轮业务代码开发范围限定为“建立唯一权威的村域候选方案评价函数，并让精确枚举与 NSGA-II 共用”。[用户已确认]
- 该评价函数必须是确定性纯评价函数；若需要修复，由外部 `repair_candidate()` 先执行，再进入评价。

### 3. 将区域协同和风险路径嵌入评价链

- 把风险路径读取、关键路径覆盖判定、风险权重聚合和区域协同纳入候选方案评价链。
- 保证区域协同在形成村域四目标之前完成。
- 保证地图展示、韧性评价和区域协同分析使用同一套路径数据。

### 4. 让精确枚举调用统一评价函数

- 精确枚举只负责遍历和筛选候选方案。
- 所有目标值、可行性、解释字段都来自统一评价函数。

### 5. 让 NSGA-II 调用同一评价函数

- NSGA-II 只负责搜索，不得改写评价逻辑。
- 个体修复、约束状态、目标值、可解释中间结果全部来自统一评价函数。

### 6. 补充约束、修复和测试

- 统一接入准入、互斥、预算、安全底线和必要的区域协同约束。
- 重写离散编码下的修复逻辑。
- 新增“区域协同进入优化链”“路径数据源统一”“精确枚举与 NSGA-II 同评分”的测试。

### 7. 再调整页面流程

- 在后台评价链正确后，再调整网页步骤文案与模块顺序。
- 第4步改为区域协同规则配置。
- 第7步改为“Pareto方案与村域协同结果解析”，不再首次计算协同结果。

### 8. 最后进行地图完善和界面优化

- 在正式评价链稳定后，再处理真实空间路径、地图表达、交互和界面优化。
- 避免 UI 先行掩盖方法链尚未闭环的问题。

## 3. 第一轮代码修改的最小文件范围建议

- `model/evaluation.py`
- `model/regional.py`
- `model/spatial.py`
- `model/solver.py`
- `model/nsga2.py`
- `model/constraints.py`
- `model/schemas.py`
- `ui_v3.py`
- `tests/test_acceptance.py`
- `tests/test_round2.py`
- `tests/test_round3.py`

其中前六个文件用于重建权威评价链，`ui_v3.py` 仅在后台顺序修正后做页面解释与流程同步，测试文件用于补齐一致性验证。

## 4. 第一轮代码验收标准

1. 存在唯一的候选村域方案评价入口。
2. 精确枚举不再自行拼装另一套目标值。
3. NSGA-II 个体评价调用同一评价入口。
4. 区域协同结果参与四目标值形成。
5. 区域协同结果能够改变 Pareto 支配关系。
6. 地图和评价使用统一 `topology` 数据结构。
7. `LCI` 用于经济性目标。
8. 货币化全寿命周期成本用于预算约束。
9. 所有待标定参数具有明确状态标记。
10. 评价函数返回可解释中间结果。
11. 相同候选方案通过精确枚举和 NSGA-II 评价时，目标值和约束状态完全一致。
12. 现有可复用测试继续通过，并增加针对统一评价链的测试。

## 5. 当前不建议优先做的事项

- 不建议先调整页面顺序。
- 不建议先增加新图表或地图美化。
- 不建议先扩展部署、数据库或云端架构。
- 不建议先继承 MATLAB 参数敏感性结果作为工程默认参数。
- 不建议因后续统一界面需求而重写计算引擎。
