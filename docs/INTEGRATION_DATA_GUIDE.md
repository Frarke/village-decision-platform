# 集成方资料清单：提供什么，得到什么

最终业务用户的操作应是：**选择研究范围 → 确认已有评价成果 → 填写预算 → 点击计算 → 查看空间治理方案**。业务用户不需要编写JSON、确定U01编号或理解遗传算法。宿主平台负责从自己的数据库或文件上传界面，把下列资料提交给本模块。

## 1. 输入资料及责任

|资料|由谁提供|示例文件|实际用途|当前要求|
|---|---|---|---|---|
|村庄或研究范围面|宿主GIS/项目管理|boundary.geojson|限定计算范围，提供真实坐标|必须；WGS84面，不能只有地图截图|
|前序风险、危险性评价成果|前序地灾评价模块|risk.tif、haz.tif|识别重点区域、措施准入|必须；1～5等级；不是由本模块重复评价|
|坡度与承灾体邻近距离|地形/承灾体分析模块|slope_deg.tif、distance_m.tif|地形筛选、≤100米邻近关系|必须；度、米；当前需上游给出|
|易发性、易损性成果|前序地灾评价模块|susceptibility.tif、vulnerability.tif|观察空间分布、统计生成单元的评价属性|可提供；0～1；不能擅自代替风险等级或工程稳定性|
|工程调查属性及其空间归属|调查/勘察人员，或宿主已存调查库|profile_id.tif、engineering_profiles.csv|坡高、FS0、降雨折减、施工空间、排水/锚固条件等|必须；调查区不是最终治理单元|
|显式风险权重及风险路径的空间记录|课题方法配置/项目调查成果|decision_context.geojson|区域重要度、物源—输移—承灾关系|必须显式提供或声明已复核无路径；不得靠底图猜测|
|预算与项目设置|业务用户/项目负责人|project.json|预算约束；算法及空间规则可由平台预置|必须；业务用户通常只需填写预算|
|工程措施库及效果参数|本课题维护，宿主可预置|当前内置八类措施|各措施准入、费用与四目标评价|无须每次上传；当前默认效果和费用待标定|

**只有易发性、易损性两张图还不够。** 它们确实是已有上游成果输入，但现有正式方法还需要风险/危险性与工程调查条件。报告没有给出可据两张图直接推导全部工程参数的公式，本模块不会暗中生成。

地图瓦片/卫星影像是定位与解释底图，不是风险计算输入。若未来用真实DEM提取坡度、坡单元、汇流和路径，需要新增相应地形计算步骤；当前没有把影像当作DEM。

## 2. 治理单元究竟由哪些文件计算

`boundary.geojson`限定范围；`risk.tif`、`distance_m.tif`及已有隐患标记决定重点像元。沿用报告规则：风险等级≥3 **或** 距承灾体≤100米 **或** 已识别隐患/重点关注。

程序把命中像元裁剪后，在同一调查属性区内识别共边连续斑块，过滤过小斑块，按配置合并/拆分并编号。生成的面边界是这些像元的空间并集，绝非从U01～U04面文件直接载入。随后统计面积、风险、坡度、易发/易损性，并关联工程调查条件。

V1.1的培田样例输入为48×48、40米像元的连续模拟评价场。实际裁剪后有1,911个有效像元，273个重点像元，形成4个不规则单元。输入中没有治理单元几何或编号。改变风险/距离数据会改变重点范围和单元数量；这已纳入回归测试。

当前边界仍是“风险重点斑块＋调查属性区”规则，不等同于地貌坡单元或勘察确定的工程边界。精细单元划分是后续研究事项。

## 3. 不用预填U01的空间权重与路径

`decision_context.geojson`采用WGS84 FeatureCollection，并声明`source`和`data_status`。记录只有两类：

- `kind=weight`：Point，属性包含唯一`record_id`及显式`risk_weight`。点落入哪个生成单元，该权重就赋给哪个单元；原数值不变，评价器统一归一化。
- `kind=path`：LineString恰有三个坐标，依次为物源、输移、承灾环节；属性包含`record_id`、`name`及布尔`key`。程序按坐标定位单元，得到评价器和地图共用的路径。

每个生成单元必须且只能对应一个权重点。点落在空白、被过滤区域、多个单元边界，或者单元内权重点重复，都明确报错，不能自动最近邻或任意平均。没有路径时必须在集合上声明`status=confirmed_empty`；这不是缺资料的替代写法。

权重点和路径是已知信息的空间表达；本轮没有新增权重公式或DEM自动路径算法。调用方也可继续使用V1按编号传参方式，但不能和空间绑定方式混用。

## 4. 一次提交、一次计算

可运行资料包：`data/v1_1/peitian_input_package.zip`。解压可看到各个真实GIS文件及调查CSV，无预定义单元文件。全部栅格需同CRS、网格、分辨率和范围；不一致会指出文件名。NoData不会当作零风险。

```http
POST /optimize-package
Content-Type: application/zip

<项目ZIP二进制内容>
```

默认返回JSON；`?view=html`返回可直接放进iframe的完整交互地图HTML。可选`&total_budget=400`覆盖本次预算，会进入模型输入和结果标识。没有模拟进度；返回前执行实际空间分析与优化。

集成方可直接运行`http://127.0.0.1:8017/integration`验证“文件输入＋预算＋计算＋结果”流程。它直接调用API，不依赖Streamlit。源代码为`assets/integration_client.html`，供对接参考；真实部署由宿主平台接管鉴权、跨域和异步作业。

已有平台可以继续`POST /optimize`提交JSON；分文件资料仅由适配器组装成同一个请求，不产生另一套评价器。`POST /prepare-package`用于仅校验和预览分区，业务上不是必须额外点击的步骤。

## 5. 最终给对方什么

|返回内容|字段/文件|宿主平台如何使用|
|---|---|---|
|重点治理范围|priority_areas|地图叠加，解释哪些地方需要治理|
|生成治理单元及来源|governance_units|显示边界、编号、属性、来源像元和候选措施|
|原始评价层|evaluation_areas|回看输入，不必从截图反推计算依据|
|五类代表方案|representative_solutions|综合均衡、安全、经济、韧性、可持续方案切换|
|方案空间面|map_result.solutions|对每个单元显示措施、费用、前后安全/韧性等|
|措施位置与图标索引|map_result.measure_placements|Point GeoJSON；含unit_id、measure_id、symbol_key、坐标|
|八类措施图标|GET /symbols/M01.svg等；成果包symbols目录|直接作为宿主地图标记，不依赖本页面|
|完整指标与非劣集|summary、metrics、pareto_front|显示比较图、约束状态、真实代数与解数|
|可嵌入地图HTML|spatial_decision_map.html|宿主iframe展示，或下载独立打开|
|可追溯成果包|decision_results.zip|保存JSON、GeoJSON、符号、图表数据和地图|

所有方案和图标来自同一求解结果快照，切换方案不会调用一套独立“展示评分”。工程图标位置采用单元内部代表点，`is_design_location=false`；图标数不是抗滑桩根数或工程量。当前输出回答“哪个治理范围采用哪些技术组合”，不能回答准确挡墙轴线、桩长桩距、施工顺序和工程量清单。

## 6. 当前数据真实性

培田村位置来自OpenStreetMap node8199467914，坐标116.6346480、25.6390104。在线地理底图与卫星影像为真实底图，保留来源署名。示例研究范围不是法定村界；范围、风险、易发/易损性、坡度、距离、调查条件、权重点与路径均为MOCK，不能据此判断培田村的真实地灾情况。

真实工程接入时替换同结构输入资料并复核参数，不需要推翻服务与求解架构。仍需补齐：真实调查与地形资料、正式权重/路径生成依据、工程量计价、措施效应标定，以及宿主的生产部署设施。
